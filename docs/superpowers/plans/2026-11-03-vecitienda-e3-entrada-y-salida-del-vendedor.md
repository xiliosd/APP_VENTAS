# VeciTienda E3 — Entrada y salida del vendedor — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A vendor joins the shared store from their own phone. They enter the store code, their
vendor number and their PIN, and the admin approves the phone from theirs. The admin can
deactivate the vendor, which blocks their PIN, closes the app on the vendor's phone and wipes the
store data from it after it hands over its pending movements. PINs stop travelling in readable
form.

**Architecture:**
- **Vendor identity.** Each phone gets its own **anonymous Supabase session**
  (`signInAnonymously`). A `miembros` row for that session goes
  `pendiente → aprobado | rechazado → revocado`. RLS already gives data only to `aprobado`
  members (E2).
- **Server-side PIN.** A new table `pines` keeps a bcrypt hash per user (pgcrypto) plus an
  attempt counter and a lock. RPCs check PINs and register them; no one can read the table.
  `pin_hash` no longer travels in `filas`: it stays on each phone. A user row that arrives from
  the cloud has an empty local hash, so the first login of that user on that phone is checked
  online and then cached locally. After that, login works offline as today.
- **Join, approve, revoke** go through RPCs with SECURITY DEFINER and explicit checks. The vendor
  phone polls its request state while it waits. The admin phone reads pending requests on every
  sync cycle and shows them with the app open.
- **Revocation.** Every sync cycle asks the server for this phone's membership. If it is
  `revocado`, the phone hands over its pending **movements** dated before the revocation (spec
  §7 call 9). It then wipes the store data and its preferences, closes the session and returns
  to the welcome screen.
- The sync **protocol goes to 2**. Old E2 builds stop syncing, so they cannot push `pin_hash`
  again.

**Tech Stack:** Flutter 3.47.2, Drift, supabase_flutter 2.18.0 (anonymous auth, RPC),
Postgres 17 with pgcrypto (`extensions` schema, already installed). No new Dart dependencies.

**Spec:** `docs/superpowers/specs/2026-11-03-vecitienda-tienda-compartida-design.md`
(§5 "Entrada del vendedor" and "Salida del vendedor", §6 PIN constraint, §7 calls 4–6, 9–11).
E2 plan: `docs/superpowers/plans/2026-11-03-vecitienda-e2-nube-y-sincronizacion.md`.

## Global Constraints

- Local schema 12 → **13**. Steps run inside the `transaction()` wrapper in `onUpgrade`.
- `versionProtocoloSincronizacion = 2`. The cloud sets `version_protocolo_minima = '2'` in the
  same migration that strips `pin_hash` from `filas`.
- **Manual step for the user**, before testing on the phone: Supabase dashboard →
  Authentication → Sign In / Providers → **enable "Allow anonymous sign-ins"**. The MCP cannot
  change it. Anonymous users can never create stores (`crear_tienda` already refuses them).
- PIN attempts: **5 failures per (store, user) → locked for 15 minutes**. This applies to both
  join and online login. Message: **"Demasiados intentos. Espera 15 minutos."**
- Store code: **6 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789`** (no 0/O/1/I/L), unique,
  generated by the server.
- Vendor number: integer ≥ 1, unique per store. The admin's phone assigns it as `max + 1` among
  vendors (only the admin creates users).
- Creating a vendor or resetting a PIN in a **shared** store needs internet, because the PIN is
  registered on the server. Offline it shows **"Necesitas internet para guardar el PIN en la
  tienda compartida."** and saves nothing.
- Naming in Spanish without abbreviations. Copy in Spanish, never raw errors. `dart format` only
  on touched files, `flutter analyze` clean, full `flutter test` green before each commit.
- Conventional Commits with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Commit
  and push to `master`.
- SQL: migration file under `supabase/migrations/`, applied with MCP `apply_migration`; a
  verification SQL under `supabase/tests/` runs first (RED) and after (GREEN), always ending in
  ROLLBACK. `get_advisors(security)` must show no ERROR.
- Logs never print PINs, hashes, emails or row data.

## Review Focus

1. **Brute force of the join.** Wrong code, number or PIN must not reveal which part was wrong.
   Attempts are limited per (store, user), and a locked user stays locked even with the right
   PIN. Test in Task 1 (SQL).
2. **A revoked phone that was offline for days.** When it reconnects it delivers only movements
   dated before the revocation, the server rejects anything else, and the wipe happens even if
   the delivery fails for a reason other than the network. Tests in Tasks 1 and 6.
3. **A user row from the cloud must never overwrite a local PIN with an empty one**, and a PIN
   reset on the admin phone (higher `version_pin`) must clear every other phone's cached hash.
   Test in Task 2.
4. **An offline first login** of a user whose local hash is empty must say clearly that internet
   is needed. It must not count as a wrong PIN. Test in Task 3.
5. **Approve or reject while the vendor phone is closed.** When the vendor reopens the app, it
   resumes from the right state: waiting, approved (download) or rejected (message). Test in
   Task 4.

### Task 1: Cloud schema for vendors and PINs

**Files:** `supabase/migrations/20261104000000_vendedores.sql`,
`supabase/tests/vendedores_prueba.sql`

**Interfaces (all `public`, functions `security definer set search_path = ''`, `revoke ...
from public, anon`, `grant ... to authenticated`):**

- `tiendas.codigo text unique not null`. Backfill existing rows; `crear_tienda` generates it
  with the Global Constraints alphabet and retries on collision.
- `miembros` gains:
  - `usuario_id_global text` (the vendor's local user; null for the admin)
  - `nombre_celular text`
  - `solicitado_en timestamptz default now()`
  - New RLS select policy: the store admin sees every `miembros` row of their store
    (`exists admin aprobado of same tienda for auth.uid()`).
- `pines`:
  - columns:
    - `tienda_id uuid references tiendas on delete cascade`
    - `usuario_id_global text`
    - `hash text` (bcrypt)
    - `hash_legado text` (sha256 hex from E1/E2 phones)
    - `version int not null default 0`
    - `intentos int not null default 0`
    - `bloqueado_hasta timestamptz`
    - `activo boolean not null default true`
  - `primary key (tienda_id, usuario_id_global)`
  - RLS enabled with **no policies**: only the RPCs touch it.
- A private helper `_pin_valido(p_tienda, p_id_global, p_pin) returns text` returns one of
  `'ok' | 'incorrecto' | 'bloqueado' | 'inactivo'`.
  - It compares bcrypt `crypt(p_pin, hash)`, or `encode(digest(p_pin,'sha256'),'hex') =
    hash_legado`.
  - When the legacy hash matches, it upgrades: sets `hash` to bcrypt and nulls `hash_legado`.
  - A failure increments `intentos`. At 5 it sets `bloqueado_hasta = now() + 15 min` and
    resets the counter. Success resets `intentos`.
- RPCs:
  - `codigo_tienda(p_tienda uuid) returns text`: approved members only.
  - `guardar_pin(p_tienda uuid, p_id_global text, p_pin text, p_version int)`: admin only.
    Upserts the bcrypt hash, clears `hash_legado`, `intentos` and the lock, and sets
    `activo = true`.
  - `guardar_pin_legado(p_tienda uuid, p_id_global text, p_hash text, p_version int)`: admin
    only. It inserts only when there is no row for that user.
  - `pines_faltantes(p_tienda uuid) returns setof text`: admin only. It returns the `id_global`
    of every `filas` row of `tabla = 'usuarios'`, not deleted, that has no `pines` row.
  - `verificar_pin(p_tienda uuid, p_id_global text, p_pin text) returns text`: approved members
    only. It returns the helper's result.
  - `solicitar_ingreso(p_codigo text, p_numero int, p_pin text, p_celular text) returns jsonb`:
    - Any authenticated user (anonymous allowed).
    - It finds the store by `upper(p_codigo)` and the vendor by
      `filas.datos->>'numero_vendedor' = p_numero::text and datos->>'rol' = 'vendedor' and
      coalesce((datos->>'activo')::boolean, true)`.
    - A missing store or vendor returns `{"resultado":"incorrecto"}`. That is the same answer
      as a wrong PIN, so it does not reveal which part was wrong.
    - It checks the PIN with the helper. On `ok` it upserts `miembros (tienda, auth.uid(),
      'vendedor', 'pendiente', id_global, p_celular)`. If that member is already `aprobado`, it
      keeps it.
    - It returns `{"resultado":"ok","tienda":…,"nombre_tienda":…,"nombre_vendedor":…}`, or the
      helper's code.
  - `mi_membresia() returns jsonb`: `{tienda, rol, estado, revocado_en, usuario_id_global}`
    for `auth.uid()`, or null.
  - `responder_solicitud(p_tienda uuid, p_usuario uuid, p_aprobar boolean)`: admin of the
    store only. It moves a `pendiente` row to `aprobado` or `rechazado`.
  - `revocar_celular(p_tienda uuid, p_usuario uuid)`: admin only. It sets `revocado` and
    `revocado_en = now()`. The admin's own row cannot be revoked.
  - `desactivar_vendedor(p_tienda uuid, p_id_global text)`: admin only. It revokes every member
    with that `usuario_id_global` and sets `pines.activo = false`.
  - `entregar_pendientes(p_filas jsonb) returns int`:
    - The caller must be `revocado` and within 30 days of `revocado_en`.
    - It accepts only **new** keys in `ventas, lineas_venta, pagos_fiado, gastos,
      conteos_inventario, entradas_mercancia, lineas_entrada, correcciones`.
    - Tables with `fecha` need `(datos->>'fecha')::bigint < extract(epoch from revocado_en)`.
    - Line tables (`lineas_venta`, `lineas_entrada`) need their parent already present in
      `filas`, inserted first in the same call or earlier.
    - It inserts into `filas`, bypassing RLS as the definer, and returns how many it accepted.
- Data step: `update filas set datos = datos - 'pin_hash' where tabla = 'usuarios'`.
- Protocol step: `update configuracion_app set valor = '2' where clave =
  'version_protocolo_minima'`.

- [ ] **Step 1: Write the verification SQL.** It begins, creates auth users A (admin, email)
  and V (anonymous, with the `is_anonymous` claim), and switches claims with `set local`. It
  asserts:
  - Store code: `crear_tienda` returns a store whose `codigo` matches
    `^[ABCDEFGHJKMNPQRSTUVWXYZ2-9]{6}$`.
  - PIN registration and join: A inserts a `filas` usuarios row with `numero_vendedor 1` and
    rol `vendedor`, and calls `guardar_pin(..., '1234', 1)`.
    - V calls `solicitar_ingreso(codigo, 1, '0000', 'Redmi')` and gets `incorrecto`.
    - V calls it with a wrong code and gets `incorrecto` too, the same answer.
    - V calls it with `'1234'` and gets `ok`; V's `mi_membresia()` is `pendiente`.
  - Lock: 5 wrong PINs and then the right one returns `bloqueado`.
  - Access before approval: V selects `filas` and gets 0 rows (pending).
  - Approval: A calls `responder_solicitud(true)`, then V sees the rows.
  - Revocation and delivery: A calls `revocar_celular`, then V selects `filas` and gets 0
    rows.
    - V's `entregar_pendientes` accepts a new venta with an earlier `fecha`.
    - It rejects a venta dated after the revocation, and rejects an update of an existing key.
  - Admin only: V cannot call `guardar_pin`, `responder_solicitud` or `desactivar_vendedor`
    (insufficient_privilege).
  - Legacy PIN: `guardar_pin_legado` with `sha256('4321')`, then `verificar_pin('4321')` is
    `ok`, and afterwards `hash_legado` is null.
  - Ends with `select 'todas las comprobaciones pasaron'; rollback;`.

- [ ] **Step 3: Apply** the migration with MCP `apply_migration` (name `vendedores`) and save

- [ ] **Step 4: Run** the verification SQL — Expected: `todas las comprobaciones pasaron`; 0

## Rulings made while planning (for the reviewer)

- **Admin phones are not listed or revoked one by one.** They share one email session, so the
  server cannot tell them apart without a device identity that RLS could check, and that is not
  possible with the anon key. A lost admin phone is handled by signing out all sessions later
  (proposed for E4). Cost if wrong: a lost admin phone keeps access until then.
- **PINs leave `filas`, and the server keeps bcrypt with attempt limits.** The first login of a
  user on a new phone needs internet once. This meets spec §6 ("no se pueda sacar con fuerza
  bruta barata") without weakening offline selling after that first login. Cost if wrong: an
  admin recovering on a new phone with no internet cannot enter until they connect.
- **Legacy PINs.** sha256 values already on phones are uploaded once as `hash_legado` and
  upgraded to bcrypt at the first successful check, so nobody has to type their PIN again.
- **A revoked phone gets 30 days to deliver** its old movements; after that it just wipes.
- **Protocol 2.** E2 builds stop syncing until updated; there is only one E2 phone (the user's).
